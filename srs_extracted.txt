[43] Heading 1: Introduction
[45] Body Text: The purpose of this Software Requirements Specification (SRS) is to provide a comprehensive and detailed description of the HotelEase system — a web-based Property Management System (PMS) developed for the Bachelor of Science in Hospitality Management (BSHM) department. This document defines the functional and non-functional requirements necessary for the successful development, deployment, and maintenance of the software, ensuring a shared understanding among developers, testers, stakeholders, and academic advisors.
[47] Body Text: HotelEase is a web-based hotel/property management system that simulates a real-world hotel environment to support academic learning, departmental operations, and practical training for BSHM students. The system mirrors industry-standard PMS workflows while being tailored to the academic context of the institution.
[48] Body Text: Key features of the platform include:
[49] List Bullet: Room Management: Administrators can add, edit, activate, and deactivate rooms with details such as room type, rate, amenities, floor, and photo gallery.
[50] List Bullet: Online Booking: Guests can browse available rooms, select dates, and submit booking requests. The system includes double-booking prevention with date-overlap validation.
[51] List Bullet: Booking Lifecycle: Full workflow from Pending → Approved → Checked In → Checked Out → Cancelled, with Front Office (FO) staff managing approvals, check-ins, check-outs, and a new FO-mediated cancellation flow (Cancellation Requested state).
[52] List Bullet: Housekeeping Workflow: Automated room status transitions (Dirty → Being Cleaned → Pending Approval → Available) with audit logging of all status changes.
[53] List Bullet: Payment Processing: Support for 4 methods (GCash, Bank Transfer, Credit/Debit Card, Over-the-Counter). Features proof-required vs proof-exempt logic, Full/Partial payment types, 48-hr payment deadline with auto-expiry, balance overpayment validation, folio management, and PDF receipt generation via jsPDF.
[54] List Bullet: Announcements & Events: FO staff can create, edit, and publish announcements with optional image uploads via Cloudinary, visible on the guest-facing landing page.
[55] List Bullet: Guest Reviews & Testimonials: Guests can submit star-rated reviews for rooms and general testimonials, with FO moderation (approve/reject) for testimonials.
[56] List Bullet: AI Chatbot: A Groq-powered (LLaMA 3.1 8B) chatbot widget on the landing page that answers hotel-related inquiries using real-time room data.
[57] List Bullet: In-App Notifications: Real-time notification system for booking events, housekeeping alerts, announcements, and support messages across all user roles.
[58] List Bullet: Contact & Support Messaging: Guests can submit support messages; FO staff can view, mark as read, and reply with optional email notification (via Cloud Functions if deployed, otherwise handled via in-app notifications).
[59] List Bullet: Analytics Dashboard: Admin dashboard showing occupancy rates, revenue summaries, booking trends (7-day chart), and peak booking periods.
[60] List Bullet: Training/Demo Mode: Admin-controlled training mode with session codes, sandboxed Firestore collections (training_ prefix), and one-click data reset for classroom use.
[61] List Bullet: Role-Based Access Control: Three distinct roles (Guest, Front Office, Admin) with Firestore security rules and client-side route protection via PrivateRoute component.
[62] Body Text: The system is not designed for comprehensive learning management (LMS) functionalities such as grading, assignment tracking, or curriculum management. It does not process real financial transactions or integrate with payment gateways for live monetary transfers.

[99] Heading 2: Product Perspective
[100] Body Text: HotelEase is a self-contained, web-based Property Management System built with a modern JavaScript stack. The frontend is a React 19 single-page application bundled with Vite 8, styled with Tailwind CSS 3.4, and enhanced with shadcn/ui components (Radix UI primitives). The backend relies entirely on Firebase services: Cloud Firestore for data persistence, Firebase Authentication for identity management, and EmailJS for client-side booking confirmation emails, and Firebase Cloud Functions (if deployed) for backend logic. Image assets (room photos, announcement images) are stored on Cloudinary CDN via unsigned uploads. The AI chatbot is powered by the Groq inference platform using the LLaMA 3.1 8B model.

The system operates independently and does not require integration with external hotel management systems. However, its modular service-layer architecture (with dedicated service files for each domain) allows for future expansion, such as integrating payment gateways or external booking aggregators.

A key architectural feature is the Training Mode, which routes all data operations to sandboxed Firestore collections (prefixed with 'training_') via a centralized utility function (getCol in db-utils.js). This ensures complete isolation between production and training data.

[194] Body Text: Hardware Limitations:

[197] List Bullet: The current version integrates with Firebase (Auth, Firestore, Cloud Functions), Cloudinary (image hosting), and Groq (AI chatbot). Future versions may integrate with payment gateways or external booking platforms.
[198] Body Text: Parallel Operation:
[199] List Bullet: The system supports multiple simultaneous users across all roles. Firestore transactions (runTransaction) are used for critical operations like booking creation, check-in/check-out, and payment recording to prevent race conditions.
[200] Body Text: Audit Functions:
[201] List Bullet: All housekeeping status changes are logged in the housekeeping_logs collection with timestamps, from/to status, and the role of the user who made the change.
[202] Body Text: Reliability Requirements:
[203] List Bullet: The system targets high availability by leveraging Firebase's managed infrastructure. Client-side error handling with graceful fallbacks ensures users are notified of failures.
[204] Body Text: Criticality of the Application:
[205] List Bullet: Medium criticality — the platform supports academic operations and training. While not life-critical, extended downtime would disrupt scheduled classroom exercises and departmental booking operations.
[206] Body Text: Safety and Security Considerations:
[207] List Bullet: Firebase Auth provides encrypted credential management. Firestore Security Rules enforce role-based access at the database level. HTTPS is enforced for all communications. Anonymous users (training mode) have restricted write access. Input validation is applied on both client and database rule levels.
