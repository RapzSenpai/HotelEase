1. Project Summary
The BSHM-PMS is a web-based Hotel/Property Management System designed specifically for the BSHM department of the school. It simulates a real-world hotel environment to support academic learning, departmental operations, and practical training for BSHM students. The system mirrors industry-standard Property Management Systems (PMS) while being tailored to the academic context.

3. User Roles
3.1 Guest (User)
• Register and log in to the system
• Browse available rooms, rates, and amenities
• Make room bookings online
• View booking status and history
• Receive email notifications
• Submit room reviews and feedback
• Interact with the AI chatbot
• Access demo mode without registration
3.2 Front Office (FO)
• Manage guest check-in and check-out
• Process payments (GCash, Cash, Check, Credit Card)
• Generate and print receipts
• Update room statuses (housekeeping workflow)
• Manage room services
• Post event announcements
• Adjust room rates
• View and manage all active bookings
• Approve or reject booking requests
3.3 Admin
• Access analytics dashboard (occupancy, revenue, trends)
• Manage user accounts and role assignments
• Configure system settings
• Reset or manage training/demo data
• Oversee full system operations

4. Core Features
4.1 Guest Management
• Guest registration form capturing: Full Name, Address, Phone Number, Email
• Optional fields: Government ID / Passport Number, Number of Guests (pax count), Special Requests
• Guest profile page showing booking history and stay details
• Returning guest detection and profile auto-fill
4.2 Room Management
Room Types (Current):
• Single Room
• Suite Room
• Presidential Room
The system is designed to be scalable — Admin can add new room types and rooms at any time.
Room Attributes per Room:
• Room number and name
• Room type
• Description
• Rate per night
• Amenities list (with icons)
• Photo gallery (stored in Firebase Storage)
• Current status
• Floor/location

4.4 Booking System
• Centralized calendar view (FullCalendar.js) showing all bookings per room
• Standard check-in time: 2:00 PM | Check-out time: 12:00 NN
• Double-booking prevention with clear error messages
• Booking types: Online (guest self-books) and Walk-in (FO creates booking)
• Night and total cost calculator on booking form
• Booking status flow:
  Pending → Approved → Checked In → Checked Out → Cancelled
• Cancellation with reason field
4.5 Payment System
Accepted Payment Methods:
• GCash (reference number capture)
• Cash
• Check (check number and bank capture)
• Credit Card (last 4 digits capture — no full card storage)
Payment Features:
• Partial payment / deposit tracking
• Guest folio (itemized billing summary per stay)
• Outstanding balance indicator before checkout
• Receipt generation (printable and downloadable PDF)
4.6 Announcements & Events
• FO can post event announcements visible on the guest-facing landing page
• Announcements include: Title, Description, Date, Image (optional)
4.7 Room Reviews & Feedback
• Guests can submit a review after checkout
• Star rating (1–5) + written feedback
• Reviews displayed on the room detail page

8. Demo / Training Mode
8.1 Demo Button (Landing Page)
• Visible to all visitors on the landing page alongside the Login button
• One-click access — no registration required
• Role selector popup: Guest, Front Office, or Admin
• Loads a sandboxed environment with pre-populated fake data
• Clear banner throughout: “Demo Mode — No real data will be affected”
8.2 Instructor Training Mode (Admin-Controlled)
• Admin can toggle Training Mode ON/OFF from the Admin dashboard
• When active, all actions are saved to a separate Firestore collection (training data)
• Students log in using school credentials or a session/class code
• Instructor can reset all training data at any time (e.g., start of new semester)
• Training session code can be generated with an expiry date
• Mirrors real hotel industry practice of sandbox environments for staff training

12. Key Technical Notes for AI Agent
• All Firebase calls should be abstracted into service files (e.g., bookingService.js, roomService.js) — never call Firestore directly from components
• Use React Context or Zustand for global state (auth state, current user role)
• Role-based route protection using React Router + custom PrivateRoute component
• Cloud Functions handle: email triggers, booking approval logic, training data isolation
• Training Mode data must be stored in separate Firestore collections (prefix: training_) to prevent pollution of real data
• Room status updates must use Firestore transactions to prevent race conditions
• FullCalendar must be connected to live Firestore booking data with real-time listeners (onSnapshot)
• All file uploads (room images, receipts) go through Firebase Storage with organized folder structure: /rooms/{roomId}/, /receipts/{bookingId}/
• Receipt PDF generation can be done client-side using jsPDF or react-pdf
• Environment variables for all API keys — never hardcoded
