HOTEL HOSPITALITY MANAGEMENT SYSTEM (HotelEase)
SYSTEM LOGIC STUDY GUIDE
Q&A Format — Think Through Each Answer Before the Panel Asks

========================================
BOOKING LOGIC
========================================

Q: How does the system check if a room is available before booking?
A: The system doesn't just check if the room is "active" — it checks all existing bookings for that room within the requested date range. If there's any overlap between the guest's check-in/check-out dates and an existing booking's dates, the room is considered unavailable for those dates. This is the right approach because a room can be booked by multiple guests across different time periods — availability is a time-window problem, not a binary on/off problem.

Q: What prevents two guests from booking the same room for the same dates?
A: Two things work together. First, the availability check runs before a booking is created — it compares the new booking's dates against all existing bookings for that room. Second, Firestore security rules prevent unauthorized writes — only authenticated users with valid data can create a booking document. So even if two users click "Book" simultaneously, the first write to create the booking succeeds and the second booking would find the room unavailable in its own availability check.

Q: What happens when a guest cancels a booking? Does the room become available immediately?
A: Yes. When a guest cancels their booking, the booking document is either deleted or marked as cancelled. The room's availability is recalculated based on remaining active bookings, so immediately after cancellation, the date range opens up again for other guests to book. The system doesn't need any manual "release" step — cancellation automatically frees the slot.

Q: How are payments linked to bookings? Can a guest pay for a booking that doesn't exist?
A: Payments are tied to a specific booking ID. When a guest uploads payment proof, the system records which booking that payment belongs to. This means a payment can't be associated with a non-existent booking — the booking must already exist before a payment can be linked to it. The system also validates the payment amount against the booking's total cost, so overpayments and underpayments are caught at the upload stage.

Q: Why does partial payment only work with GCash?
A: Partial payment is offered for GCash because GCash is widely used and supports the flexibility of paying in installments — guests can pay a portion upfront and settle the balance later. This is a practical decision based on the payment landscape in the Philippines. Other payment methods require full payment upfront, which is enforced in the system logic.

========================================
USER ROLES & ACCESS LOGIC
========================================

Q: How does the system know whether a logged-in user is an admin, FO staff, or guest?
A: Every user has a profile document in Firestore with a role field. When a user logs in, the system reads this profile and stores the role in the application state. All route-based access control uses this role — routes like /admin and /fo are wrapped in a route guard that checks if the current user's role matches the allowed roles for that route. If it doesn't match, the user is redirected to a page that's appropriate for their role.

Q: Why are there exactly three roles instead of more?
A: Three roles represent the three distinct user interactions in this system. Guests interact with the system from the public-facing side — browsing, booking, paying. FO staff handle the operational side — approving bookings, managing check-ins, assigning housekeeping. Admins handle the configuration side — managing rooms, users, and system settings. More roles would add complexity without adding clear operational boundaries for this scope of the project.

Q: What happens if an FO staff member tries to access an admin page?
A: The route guard on the admin page checks the user's role. If the role is not admin, the navigation is blocked and the user is redirected to their appropriate home page. The admin page never renders for non-admin users. This is enforced at two levels — the frontend route guard and the Firestore security rules on the backend — so even a technically sophisticated attempt to bypass the frontend won't grant access.

Q: Can a guest's role be changed to FO or Admin from within the system?
A: Not by the guest themselves. Role changes are an admin-only operation. Admin users can view all registered users and update their roles through the user management page. This ensures that only authorized administrators can escalate privileges, preventing any guest from self-promoting to staff or admin access.

Q: How does the system handle a FO staff member viewing a guest's bookings?
A: FO staff can view bookings but only within the scope of their operational needs. The bookings page for FO staff shows all bookings that require their attention — pending bookings for approval, bookings for their assigned rooms, and bookings with payment-related actions. Guests cannot see internal FO operations or admin-only data, preserving the privacy boundary between user types.

========================================
PAYMENT LOGIC
========================================

Q: How does the system handle the difference between full and partial payment?
A: When a guest creates a booking, they select a payment type. If they choose full payment, the full booking amount is due and the payment proof upload section expects the complete amount. If they choose partial payment, the GCash partial payment calculator provides the split amount — showing how much to pay now and how much remains outstanding. The system stores the payment type and amount paid, allowing the booking to be tracked with its payment status.

Q: What happens if a guest uploads a payment proof for the wrong amount?
A: The payment proof upload accepts the file and records the payment details including the amount entered by the guest. The FO staff can then review the payment details on the payments page and verify whether the amount matches the booking's total. If there's a mismatch, the FO staff can flag it or contact the guest for clarification.

Q: Why must a payment proof be uploaded even for full payment?
A: The payment proof serves as the official record of the transaction. Even if the guest pays in full, the system requires visual confirmation — a screenshot or receipt — that the payment was actually made. This protects both the hotel and the guest, creating a verifiable trail of every financial transaction.

========================================
TRAINING MODE LOGIC
========================================

Q: What is training mode and why does the system have it?
A: Training mode is a system-wide toggle that allows the hotel to create a safe environment for staff training and system testing. When training mode is enabled, the system can simulate different configurations — like different payment rates or room availability — without affecting the live booking environment. This allows staff to practice using the system and administrators to test new features without risking real booking data.

Q: How does training mode get enabled or disabled?
A: Training mode is controlled through the system settings page, which is accessible only to administrators. The toggle switches the system between normal and training mode, and this setting is stored in Firestore so it persists across sessions and server restarts. There's also a local storage override for development purposes that takes precedence in certain conditions.

Q: Does training mode affect regular bookings?
A: Yes, but in a controlled way. Training mode may alter pricing, availability rules, or other system parameters — but these changes are intentional and part of the training environment design. Regular bookings made in training mode are clearly separated from live bookings through internal tracking.

========================================
REGISTRATION & AUTHENTICATION LOGIC
========================================

Q: Why does the system require a password with uppercase letters, numbers, and special characters?
A: This is a standard password strength requirement. Requiring multiple character types significantly increases the difficulty of brute-force attacks. A password that's 8 characters long with at least one uppercase letter, one number, and one special character has billions more possible combinations than a simple lowercase-only password of the same length.

Q: What's the cooldown mechanism after registration?
A: After a successful registration, the system imposes a 60-second cooldown before another registration can be made from the same session. This prevents automated or rapid-fire sign-ups — such as a bot registering multiple accounts in seconds. The cooldown timer is managed on the frontend with a state variable, and if a user tries to register again within the cooldown period, they get a clear message to wait.

Q: How does the system prevent bots from registering?
A: A honeypot field is hidden from human users but detectable by automated bots. The field is invisible to real users through CSS but is part of the form. If a bot fills in every form field, it will also fill in this hidden honeypot field — the system detects this and silently rejects the registration without showing an error. This is a lightweight but effective anti-bot measure for a registration form.

Q: Why does registration sign the user out automatically after creating their account?
A: This is a deliberate security and UX decision. When a user registers, they create an account but haven't logged in yet — they don't need to be authenticated immediately. Signing them out ensures that: 1) the "please log in" message makes sense because they genuinely need to create credentials first, and 2) the system doesn't accidentally create a session with incomplete profile data before the user has verified their email or completed setup.

========================================
ERROR HANDLING LOGIC
========================================

Q: Why are error messages centralized instead of scattered across each page?
A: Centralizing error messages means two things. First, consistency — every user gets the same clear message for the same error regardless of which page they're on. A "permission denied" message doesn't suddenly change wording depending on whether it happened during booking, registration, or profile editing. Second, maintainability — if we need to update or add a new error code, we update it in one place rather than hunting through every page that handles Firebase errors. This is a scalability decision that becomes more valuable as the system grows.

Q: What happens when an error code isn't in the mapping system?
A: The system has a fallback strategy. First, it checks if the error code is a known Firebase code in its internal map — if yes, it returns the human-friendly message. Second, if the code isn't recognized, it tries to strip the raw Firebase error prefix (like "Firebase: Error (code=xxx):") from the message and show the clean description. Third, if even that fails, it returns a generic "Something went wrong. Please try again." That third fallback ensures the user never sees a raw Firebase error code on screen.

Q: How does the system handle network errors differently from permission errors?
A: Network errors and permission errors have different root causes and require different user responses. A network error means the user's connection dropped — the solution is to check their internet connection and retry. A permission error means the user doesn't have the right to perform that action — the solution is to contact support or check their account permissions. The error mapping system differentiates between these so the user gets the right guidance for the right type of failure.

========================================
DATA FLOW LOGIC
========================================

Q: How does Firestore keep data in sync across multiple users?
A: Firestore has built-in real-time listeners. When data changes on the server — like when FO staff approves a booking or a guest uploads a payment proof — Firestore automatically pushes those updates to all connected clients that are listening for that data. This means if an admin updates a room's price, FO staff and guests all see the updated price in real time without needing to refresh the page. This is a fundamental advantage of Firestore over traditional database polling approaches.

Q: What happens to guest-facing data if the network disconnects mid-transaction?
A: Firestore operations that require a network connection (like creating a booking or uploading a payment proof) will fail with a network-related error if the user goes offline. The error mapping system catches these and shows a clear message like "Network error. Please check your connection and try again." The user can then reconnect and retry the operation — their partially created data doesn't corrupt the system because Firestore transactions are atomic — they either complete fully or not at all.

Q: Why is the user profile stored in Firestore separately from the Firebase Auth user?
A: Firebase Auth handles identity — who the user is (email, password, UID). Firestore stores application-specific data — what role they have, what bookings they've made, their profile preferences. Separating these concerns means: 1) the authentication system is simple and secure, 2) application data can be queried and filtered independently, and 3) changes to user roles or profile data don't require touching the authentication system. It's a clean separation that makes each part easier to maintain.

========================================
EDGE CASE LOGIC
========================================

Q: What happens if a guest tries to book a room that was deleted or archived between when they loaded the page and when they clicked "Book"?
A: The system handles this gracefully. If the booking creation tries to reference a room that no longer exists in Firestore, the operation will fail. The error mapping system catches this and shows the user a friendly message like "This room is no longer available." They're then free to choose a different room without any confusing technical error.

Q: What if a guest tries to book for dates in the past?
A: The booking form validates the dates before submission. If the check-in date is in the past or the check-out date is before the check-in date, the form shows a validation error and prevents submission. This client-side validation prevents unnecessary Firestore writes and gives the user immediate feedback about what's wrong with their selection.

Q: How does the system handle a FO staff member trying to check in a guest who hasn't completed payment?
A: The check-in process can be designed to require payment completion first — this is a business rule enforced by the system. If the booking status shows "pending payment," the FO staff is presented with this status and can't proceed to check-in until payment is confirmed. This prevents the operational issue of a guest staying without paying.

Q: What happens to a guest's review if the room they reviewed is later archived by an admin?
A: The review remains attached to the room. Archiving a room doesn't delete related data — it just changes the room's status so it's no longer visible for new bookings. Reviews from guests who stayed at that room remain intact and are still visible if the room is unarchived and made bookable again. This ensures guest feedback is preserved even when the underlying data changes.

========================================
SECURITY LOGIC
========================================

Q: Why are Firestore security rules important even though the frontend handles access control?
A: The frontend access control is there for user experience — it shows the right buttons and pages for each role. But a malicious user could bypass the frontend by crafting direct requests to Firestore. Security rules act as the final gatekeeper — they enforce permissions at the database level, so even requests that bypass the frontend are rejected by Firestore. Both layers are necessary: frontend for UX, backend rules for true security.

Q: Can a regular user read another user's data through Firestore queries?
A: No. Firestore security rules restrict read access so that users can only read documents they're authorized to see. A guest user cannot query another guest's booking data because the security rules require matching UIDs. FO users can only see booking data relevant to their operational scope. Admin users can see all user data across roles, but this is intentional and controlled through their elevated privileges.

Q: How does the system handle uploaded files securely through Cloud Storage?
A: Files uploaded by guests for payment proof go through Cloud Storage with a specific path structure that includes the booking ID and user UID. The storage rules restrict who can upload and download files — guests can only upload for their own bookings, and FO/admin users can download files relevant to their scope. The file path includes metadata that prevents users from guessing or accessing other users' upload paths.
